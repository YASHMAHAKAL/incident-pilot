# Phase 11: GitHub remediation pull request

Phase 11 extends the existing `request_remediation` boundary. It does not add a `github_create_pr` MCP tool. A single request now follows this trusted sequence:

```text
validate proposal and evidence
  -> derive trusted risk attributes
  -> evaluate OPA
  -> if denied: persist denial, do not call GitHub
  -> if allowed: read fixed repository/base branch/path
  -> generate one constrained YAML scalar edit
  -> create/reuse deterministic branch
  -> commit the one file
  -> create/reuse pull request
  -> persist proposal, decision, PR result, and audit event
```

An allowed policy decision is necessary but not sufficient for a PR. Patch applicability and every GitHub response are validated again. GitHub failures are recorded as `PR_FAILED` with a bounded failure code; credentials and response bodies are never returned. A successful or reused pull request produces `PR_CREATED` and includes only its repository, base/head branches, number, HTTPS URL, commit SHA, and reuse flag.

## Constrained patch

The v1 generator supports only the policy-approved OOM repair:

- repository and path must equal trusted API configuration
- resource must be the `incidentpilot-demo/payments-api` Deployment
- container must be `payments-api`
- field must be `memory_limit`
- the YAML must contain exactly one matching memory scalar
- repository content must still equal the evidence-backed `before` value
- only that scalar is replaced; the file is not reformatted

The policy continues to bound the increase to at most 4x and 512 MiB. For the local fixture the proposed repair is `48Mi -> 128Mi`. If the configured base branch already contains `128Mi`, the adapter returns `patch_not_applicable`; it does not manufacture an unrelated diff.

Branches are deterministically named from the investigation UUID, for example `incidentpilot-oom-351569fab89b`. Before writing, the adapter looks for an existing open PR with that head/base pair. A retry reuses that PR. If a partial attempt left a branch, its file must equal either the base content or the exact generated patch; any divergence fails closed.

## Credentials and configuration

GitHub write configuration belongs only on `incidentpilot-api`:

```text
INCIDENTPILOT_GITHUB_WRITE_API_URL=https://api.github.com
INCIDENTPILOT_GITHUB_WRITE_TOKEN=<short-lived token>
INCIDENTPILOT_GITHUB_BASE_BRANCH=main
```

Use a GitHub App installation token when available. For local development, a fine-grained token should be restricted to `YASHMAHAKAL/incident-pilot` with only repository Contents read/write and Pull requests read/write. Do not reuse the Phase 8 MCP read token, put a write token in `.env.example`, or send it to an LLM.

The kind API Deployment optionally imports a Secret named `incidentpilot-github-remediation`. Create it locally without committing it:

```sh
kubectl --context kind-incidentpilot -n incidentpilot-system create secret generic incidentpilot-github-remediation \
  --from-literal=INCIDENTPILOT_GITHUB_WRITE_API_URL=https://api.github.com \
  --from-literal=INCIDENTPILOT_GITHUB_WRITE_TOKEN='<token>' \
  --from-literal=INCIDENTPILOT_GITHUB_BASE_BRANCH=main
kubectl --context kind-incidentpilot -n incidentpilot-system rollout restart deployment/incidentpilot-api
```

Configuration is all-or-none. Without it, an OPA-allowed request is durably recorded as `PR_FAILED/github_not_configured`; a denied request remains `POLICY_DENIED` and never needs GitHub configuration.

## Pull-request content

The commit title and PR text are generated by trusted code. The PR body contains the incident UUID, investigation UUID, policy version, evidence UUIDs, and exact before/after values. It does not include evidence payloads, logs, model prose, credentials, or arbitrary proposal text. Human review and merge remain mandatory; IncidentPilot never merges the PR or mutates Kubernetes directly.

## Verification boundary

Unit and adapter tests exercise the exact GitHub request sequence, one-scalar patch, idempotent PR reuse, denied-policy non-execution, failure persistence, unsafe URL/path rejection, and policy bypass prevention. A live PR additionally requires a write credential, a fresh Phase 10-aware OOM investigation, and a configured base branch whose manifest still contains the observed `48Mi` fault. The normal `main` branch intentionally contains the healthy `128Mi` baseline, so a live request against it correctly fails patch applicability rather than opening an empty or misleading PR.

## Live evaluation (2026-09-22)

A fresh alert-driven OOM run created incident `8a25936b-78b7-48de-a0f7-f1f9b8dc3df3`. Investigation `e16f7037-9a4f-40e0-8367-7e6595b972ac` reached `ROOT_CAUSE_FOUND` only after the deterministic verifier corroborated a `payments-api` `OOMKilled` record with the observed `48Mi` Deployment limit. The fixture was then reset to `128Mi`.

The first policy-approved execution failed closed as `PR_FAILED/github_pr_lookup_failed`. Its trace identified a missing CA bundle in the scratch API image, so the runtime image now includes Alpine's trusted certificate bundle. Retrying the unchanged proposal created [PR #1](https://github.com/YASHMAHAKAL/incident-pilot/pull/1) from `incidentpilot-oom-e16f70379a4f` into the isolated `incidentpilot-eval-oom-base` branch. The PR contains exactly one file and one scalar change, `48Mi -> 128Mi`. A second identical request reused PR #1 and persisted `reused=true` rather than creating another branch or pull request.

PostgreSQL retained the failed attempt, successful creation, policy decisions, pull-request records, and audit outcomes. The evaluation credential was removed from the kind cluster afterward. PR #1 remains open and unmerged for human review; normal `main` remains at the healthy `128Mi` baseline.
